AtomicPass

Concurrency-safe, rush-proof event ticketing

A college fest releases 5,000 passes at 6 PM. About 5,000 students press Buy in the same second.

1
Never oversell. Not by one ticket, not across tiers, not under concurrency.
2
Free the seats of checkouts nobody pays for, so others can buy them.
3
Admit each pass exactly once at the gate.
We read how Hi.Events (open source, PHP/Laravel) handles this, listed where it is weak, and rebuilt the core in TypeScript so that each rule is one atomic database step that a test tries to race.
One processOne SQLite fileNo external serviceNo API keyNo AI in the product

Two improvements on top of the baseline:
Fix: capacity enforced on tier and event pool, counting holds (GAP-1).
Differentiator: a waiting room and a per-buyer cap.

The design

Every rule is one conditional update that a test races

A held and a sold counter on every tier and on the event pool. The number of rows an UPDATE changes decides who won.

differentiator

1 · Waiting room

First come, first admitted; a few per tick. An admission is used up only by a hold that succeeds. Per-buyer cap on the normalised email.
the fix

2 · Hold

One BEGIN IMMEDIATE: tier, then pool.
UPDATE tiers SET held=held+q
 WHERE cap-sold-held >= q;
UPDATE events SET held=held+n
 WHERE cap-sold-held >= n;
0 rows changed: refused, all rolled back.

3 · Pay

held → sold in the same statements, so held + sold never changes. Creates the order and one ticket per seat with a 128-bit QR token.

4 · Expire

Every reserve, pay and read frees due holds first; a sweeper only tidies up. A seat never waits for the sweeper.

5 · Gate

UPDATE tickets
 SET status='CHECKED_IN'
 WHERE qr_token=? AND
       status='VALID';
One scan wins. Refund uses the same guard, so a scan and a refund racing have one winner.
Database as the last line: CHECK (sold + held ≤ capacity) on every tier and event.
An audit after every test: counters are recomputed from the rows; any difference fails the test.
Honest ceiling: SQLite has one writer, so one machine. The same statements are documented for PostgreSQL, not run.

Demo and run

Five commands, then the live demo

# Node.js 22.12 or newer git clone https://github.com/Yash13606/debugdevise cd debugdevise npm install npm run killer npm start
Short hold lifetime for the demo. Put this in .env (copy of .env.example):
HOLD_TTL_SECONDS=2
Every setting has a default, so without .env a hold lasts 600 s.
  1. Show .env with HOLD_TTL_SECONDS=2.
  2. npm run killerlast-ticket race, pool race, an unpaid hold frees its seat, one scan per ticket, and the races across connections
  3. npm run demoten buyers join the line, three admitted per tick, an unadmitted buyer gets 403 NOT_ADMITTED, the cap refuses extra tickets with 409 BUYER_LIMIT
  4. Open the matching section of docs/ for each point.
  5. Optional: npm run rush5,000 buyers press buy at once for 4,500 seats
